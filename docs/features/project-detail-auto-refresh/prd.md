# PRD：项目详情页列表自动刷新

> Feature slug：`project-detail-auto-refresh`
> 来源任务：飞书 Valuz 清单 t100089 — 「项目详情页，没有自动刷新，有新对话或者任务从其他地方触发，无法自动出现在详情页的列表中」
> 撰写：产品负责人 ｜ 状态：评审中（第 2 轮）

## 1. 背景与目标

用户停留在某个**项目详情页**时，若从**其他入口**产生了属于该项目的新会话或新任务（例如：全局新建对话并选中该项目、定时任务/Automation 触发了任务、任务被 lead 派发、另一窗口/另一设备的操作），详情页的「会话列表」和「任务列表」**不会自动更新**——用户必须切走再切回、重进页面或重启应用才能看到。

- **解决谁的什么问题**：在项目详情页工作的用户，看不到「此刻刚刚发生」的会话/任务，对项目当前状态产生误判。
- **现在怎么解决**：手动刷新（切换项目、重进页面、重启 App）。
- **目标**：用户停留在项目详情页时，新产生的会话/任务及其状态变化能**自动、准实时**地反映到对应列表，无需任何手动刷新动作。

## 2. 列表对象定义（本版收口）

为避免「到底刷新哪张列表」的歧义，明确两个列表对象与可见规则：

- **项目会话列表**：归属当前项目、`task_id == null`（非任务内部 session）、且 `status != "created"`（已发出首条有效消息、非空白草稿）的会话。
  - 排除：处于 `created` 草稿态的新建对话、任务内部的 lead/member session、其它项目或其它用户的会话。
- **项目任务列表**：归属当前项目的**顶层 lead-dispatch Task**（即详情页任务区现有展示的对象）。
  - 排除：Task 内部的 member/subtask sub-run、Automation 的运行历史记录（run 日志）、会话消息流。Automation 仅作为「触发任务」的来源之一——它触发出的**顶层任务**纳入本列表，其 run 记录本身不纳入。

## 3. 用户故事（含权限边界）

- 作为在项目详情页的用户，当我（或定时任务/派发逻辑）在别处创建了一个归属本项目、且符合上节可见规则的会话时，我希望**无需操作**就能在会话列表看到它。
- 作为在项目详情页的用户，当一个归属本项目的顶层任务被触发（定时任务 / 手动 kickoff / lead 派发）时，我希望它**自动出现**在任务列表里。
- 作为在项目详情页的用户，当某个任务的运行状态发生**任何变化**时，我希望对应行的状态展示**自动更新**，不必刷新就知道它的最新状态。

**权限/可见性边界（贯穿所有故事）**：列表只展示**当前登录用户有权访问、且归属当前项目**的数据。自动更新通道（无论 SSE 还是轮询）必须沿用与现有接口一致的 `user_id` + `project_id` 过滤，不得展示其它项目、其它用户、或任务内部隐藏 session。

## 4. 范围

**本版要做：**
- 项目会话列表：别处新增的、符合 §2 可见规则的归属本项目会话，自动出现。
- 项目任务列表：别处触发的归属本项目**顶层任务**，自动出现。
- 任务**状态变化**在列表行上自动反映（见 §5 状态语义）。
- 列表从**空态 → 有数据**时自动切换展示。
- 自动更新通道异常时的**降级与恢复补齐**（见 §6）。

**本版不做：**
- 不做会话内部消息内容的实时流（属会话详情页职责）。
- 不做 Task 内部 member/subtask sub-run、Automation run 历史记录的列表刷新。
- 不做跨项目的全局通知/红点提醒。
- 不做列表分页、虚拟滚动等性能重构。
- 不改动列表的排序规则、筛选规则、状态文案与现有视觉样式（仅让其数据能自动更新）。

## 5. 状态语义

- 任务列表行的状态展示**直接取后端任务 `status` 字段**，沿用现有 UI（StatusPill）的既有文案与配色映射，本版**不新增、不修改**任何状态文案。
- 本版要求：任务 `status` 发生**任意变化**（进行中、完成 `completed`、停止 `stopped`、阻塞 `blocked` 等任何取值之间的转移）都需在对应列表行自动更新——不限定固定子集，避免遗漏 paused/stopped/blocked 等状态。
- 验收以「进行中 → 完成」和「进行中 → 停止/阻塞」作为代表性场景（见 §8）。

## 6. 核心交互流程与降级

1. 用户进入项目详情页 → 首屏按现有逻辑全量拉取会话与任务列表。
2. 页面停留期间，系统持续感知归属本项目、当前用户可见的会话/任务的新增与状态变化。
3. 一旦有变化，列表**自动**插入新条目 / 更新对应行状态。
4. 该过程不打断用户当前操作（见 §7 锚定规则）。
5. **降级与恢复**：自动更新通道异常时**静默降级**——不弹错误、不清空已展示列表，保留上次成功结果。**检测到通道恢复后，若用户仍停留在当前页，必须自动触发一次全量刷新以补齐遗漏的新增/状态变化**（不依赖用户重进页面）。计时起点为「检测到通道恢复」时刻。
6. 离开页面或进入其它项目时，停止对本项目的感知；再次进入时回到步骤 1。

## 7. 界面交互说明（含状态）

- **加载态**：首次进入沿用现有 loading 表现，无新增。
- **空态**：当前无会话/无任务时显示现有空态；当**第一条**数据自动到达时，自动从空态切换为列表，无需刷新。
- **自动更新（成功）**：新条目按现有排序就位；任务行 StatusPill 随状态变化更新。
- **不打断用户 + 锚定规则**：自动插入/重排时**以保持当前可见行的滚动锚点为准**——用户当前可见的内容不得发生跳动；同时**不抢占滚动位置、不清空 composer 输入、不改变当前选中/展开项**。当严格排序与锚定冲突时，**以锚定优先**（新条目可在用户回滚到顶部/对应位置时呈现）。
- **错误/降级态**：见 §6——静默降级、保留旧列表、恢复后自动补齐。

## 8. 待决策项（交技术方案权衡，PRD 不指定实现）

- 实现机制：**SSE 事件订阅** vs **轮询** vs **复用既有会话新鲜度机制并为任务列表补订阅/刷新**。PRD 只约束「自动、无需手动刷新、满足 §9 的 5 秒 SLA」，具体机制由「前后端开发」在 PLAN 中定。

## 9. 验收标准（用户视角）

**统一 SLA**：以下所有「正向自动出现/更新」类验收，均以「正常联网、页面保持打开」为前提，要求在 **5 秒内**对用户可见。

**新增条目可见性口径**：§9.1/§9.2「看到新条目」默认指列表处于其排序位置（通常为顶部）时可见；若用户当前视口不在插入位置，验收口径为「数据已进入列表且不扰动当前可见行」，**不强制**自动跳转到新条目（与 §7 锚定优先一致）。

1. 用户停在项目详情页，在别处新建了一个符合 §2 可见规则、归属本项目的会话 → 用户**无需任何操作**，在 5 秒内能在该详情页会话列表中看到这条新会话。
2. 用户停在项目详情页，一个归属本项目的顶层任务被触发（定时任务 / 手动 kickoff / lead 派发）→ 用户在 5 秒内能在任务列表看到这条新任务。
3. 某任务运行状态变化（进行中 → 完成，或 进行中 → 停止/阻塞）→ 用户在 5 秒内看到该任务行状态自动更新，无需刷新。
4. 列表从空态变为有数据时，用户看到列表**自动**从空态切换为数据展示，无需刷新（同样 5 秒内）。
5. 自动更新发生时，用户**不会**遇到当前可见行跳动、滚动位置被重置、正在输入的内容被清空、或当前选中项被改变。
6. 自动更新通道异常时，用户**不会**看到报错弹窗，也**不会**看到已有列表被清空；页面保持上次成功的列表。通道恢复后用户仍停留当前页时，遗漏的新增/状态变化在**一次自动全量刷新**后于 5 秒内补齐。
7. 用户停在**项目 A** 详情页，**项目 B** 新增会话或任务时，项目 A 的会话列表/任务列表**不出现**该条目（仅展示归属当前项目、当前用户可见的数据）。
